# Changelog

## Real-HTTP smoke test (scripts/smoke/)

- Added `scripts/smoke/fake-drupalforge-api.php`: a standalone fake DrupalForge API implementing
  all 6 contract endpoints plus a `/storage/{key}` object endpoint, backed by a JSON state file
  and a request log. Serves real HTTPS (a self-signed cert, generated by `run.sh`) via a small raw
  `stream_socket_server()` HTTP/1.1 server - not `php -S`, which has no TLS support - since the
  smoke test must exercise `DrupalForgeClient`'s real HTTPS-scheme enforcement, not a weakened path
  around it. Implements the `100 Continue` handshake explicitly (without it, a multipart PUT body
  over cURL's ~1MiB `Expect` threshold would deadlock against this server).
- Added `scripts/smoke/run.sh`: drives real `drush drupalforge-migrate:*` commands against it -
  preflight, a full happy-path backup, an interrupt-mid-upload-then-`--resume` scenario, and a
  forced-upload-failure-aborts-cleanly scenario - with a temporary `settings.php` override
  (restored exactly on exit via a trap) and a PASS/FAIL summary.
- Process management inside the DDEV container avoids `$!`/PID files entirely: `ddev exec` nests
  its own `bash -c "set -eu && (...)"` wrapper around whatever string is passed to it, so a literal
  `$!` gets evaluated at the wrong shell level and fails with "unbound variable" (verified
  empirically). `pgrep`/`pkill` with the classic `'[x]xxx'` bracket trick (so the search pattern
  doesn't match the invoking wrapper's own command line, which is otherwise an ancestor process
  that also contains the pattern) sidesteps both that and pkill/pgrep's usual self-match pitfall.
- Verified real teeth: temporarily commented out `BackupOrchestrator::abortBackup()`'s
  `client->abort()` call and confirmed `run.sh` correctly failed the forced-failure scenario
  (`abort_logged=0`) while every other scenario still passed - then reverted and confirmed all
  scenarios pass again. Also caught and fixed a genuine flaky assertion of its own along the way:
  the resume scenario's "zero duplicate part uploads" check was too strict - a part in flight at
  the exact instant of `kill -9` can legitimately be received by the server without the client
  ever recording it locally, so it's correctly re-uploaded once on resume (matches `Uploader`'s own
  documented "a crash mid-part loses at most one part's progress" guarantee) - tightened to
  "at most one" duplicate instead of zero.

## Post-Slice-3 — final cleanup pass: closing the review's remaining findings

Closes out the last items from the code review, on top of the network/orchestration and
archive/export hardening passes below.

- **`CodeArchiver::archiveViaPharData()`/`exclusionRegex()` bug fix**: the PharData fallback path
  (used when `tar`/`gzip` aren't on the host) threw `RegexIterator::__construct(): Unknown modifier
  ']'` for real exclusion lists - never caught before because no existing test actually let
  `PharData::buildFromDirectory()` run (only the CLI-available and over-ceiling-refusal branches
  were exercised). Root cause: `exclusionRegex()` used `/` as the PCRE delimiter, but its
  glob→regex translation for `settings.*.php`-style excludes injects a literal, unescaped `/`
  inside `[^/]*` - PCRE read that as an early closing delimiter, truncating the pattern and
  misparsing the rest as modifier flags. Fixed by switching the delimiter to `#` (which never
  appears in this module's path-based exclusion patterns). New regression test
  (`testArchiveViaPharDataFallbackExcludesFilesAndSettings`) forces the PharData path, confirmed it
  reproduced the exact production error before the fix, and now asserts `settings.php` and
  `sites/default/files/*` are genuinely absent from a real PharData-produced archive.
- **Resume-contract test coverage** (previously zero): `resumeBackup()`/`resumeUpload()` now have
  tests for no-current-backup, no-local-artifacts, code-only-present, both-artifacts-present, and a
  genuine "double resume" (resuming a backup a second time after it already completed) proving it's
  a safe refusal, not a crash or a re-upload.
- **`complete()`-failure test coverage** (previously zero): every artifact can upload successfully,
  but if DrupalForge's `complete()` call itself throws (a 500, a checksum rejection), the backup
  must still abort rather than being silently treated as `ready` - this is the last line of defense
  for the "never mark ready after partial failure" guarantee, and a bug that cleared progress state
  before (rather than after) a successful `complete()` call would previously have passed every test.
- **DB-export-failure orchestrator-guard test** (previously only tested at the `DatabaseExporter`
  service level, not through `BackupOrchestrator`'s `runGuarded()` wrapper): confirms an
  `ExportFailedException` from `runDbArtifactCli()` aborts exactly like archive/upload failures do.
- **Dead code removed**: `CodeArchiver::writeManifest()` (and its `CodeArchiverInterface`
  declaration) - never called; `BackupOrchestrator` sends the manifest directly in the `complete`
  request body and never persists `manifest.json` to disk. Fixed the now-stale `BackupManifest.php`
  docblock that referenced it.
- **Stale development-phase comments removed**: three "this slice"/"Slice 3"/"See TODO.md"
  references in `BackupOrchestrator.php` and `DrupalForgeMigrateCommands.php`, rewritten as
  permanent architectural explanations.
- **`DrupalForgeClient::request()` now explicitly checks the response status code** instead of
  relying solely on the injected Guzzle client's default `http_errors => TRUE` behavior throwing
  for it. A site can disable that globally via `$settings['http_client_config']['http_errors'] =
  FALSE` in settings.php (a documented, supported Drupal core override affecting the shared
  `http_client` service this module also uses) - without this check, a non-2xx response in that
  configuration would have been silently treated as success, up to and including marking a backup
  `ready` when DrupalForge's `complete` call actually failed. This was the one item from the
  original 19 findings not yet covered by the network/orchestration hardening pass below.

All 19 findings from the original code review, plus the HTTPS-enforcement follow-up, are now
addressed. 128/128 tests green (117 baseline + 11 new), no regressions.

## Post-Slice-3 — archive/export layer hardening (fail closed, not open)

Fixes from an external code review of the archive/export layer (`ShellRunner`, `CodeArchiver`,
`DatabaseExporter`, `PreflightService`). The common theme: several failure paths in this layer were
silently swallowed and treated as "0 bytes" / "empty checksum" / "placeholder DDL" - i.e. failing
*open* - rather than aborting the backup. All of the following now fail closed instead, each with a
regression test (117/117 green, no regressions).

- **`DatabaseExporter::createTableStatement()` no longer degrades a failed `SHOW CREATE TABLE` to a
  placeholder comment** - it throws `ExportFailedException` naming the table. The old behavior let
  `exportStepWeb()` go on to write `INSERT` rows for a table with no matching `CREATE TABLE`
  statement, producing a dump that would fail to restore while still being reported as a
  successful, `ready` backup.
- **`hash_file(...) ?: ''` replaced with an explicit check** in `CodeArchiver::archive()` and
  `DatabaseExporter::exportViaCli()` - a checksum read failure now throws
  `ArchiveFailedException`/`ExportFailedException` instead of silently shipping an empty (but
  "valid-looking") checksum.
- **Size-estimation failures now fail closed**: `CodeArchiver::measureDirectorySize()` (gates the
  PharData-fallback ceiling) and `DatabaseExporter::estimateSizeBytes()` (gates the web-export
  ceiling) now throw on a mid-walk/mid-query failure instead of returning `0`/a partial total, which
  previously let an unmeasurably-large site slip past the very ceiling meant to refuse it.
  `PreflightService::estimateCodeSizeBytes()`/`estimateDbSizeBytes()` (informational, not gating)
  now return `?int` and, on `NULL`, `run()` marks the preflight result unsupported with a named
  reason and reports `-1` for that check, rather than silently reporting "0 bytes" as if the site
  were fine.
- **`ShellRunner::pump()` now distinguishes a genuine `fread()` I/O error from clean EOF** (both used
  to be treated identically, silently truncating captured output on a real read error) via a new
  shared `readChunk()` classification helper, and `exec()` surfaces a read error as a failing
  `ShellResult` instead of a truncated "successful" one.
- **New `ShellRunner::runPipedToFile()`**: streams the final stage's stdout directly to a destination
  file via real OS-level pipes between stages (an already-open pipe resource handed straight to the
  next `proc_open()` call, dup'd by the kernel - no PHP-side byte copy between stages at all),
  instead of `runPiped()`'s full in-memory buffering. `CodeArchiver::archiveViaCli()` and
  `DatabaseExporter::exportViaCli()` now use it, removing the unbounded-memory risk on exactly the
  large-site case the CLI path exists for (verified live: a real ~33MB archive and ~1-1.6MB DB dump,
  neither ever fully buffered in PHP).
- **Post-write integrity verification**: `CodeArchiver::archive()` and `DatabaseExporter`'s CLI/
  finalize paths now run a cheap structural check (`tar -tzf`/`gzip -t` via `ShellRunner` when
  available, else a PHP-native `gzopen()`/`gzread()` fallback) before treating an artifact as
  successfully produced - "a file exists at this path" was previously the only check. Also:
  `DatabaseExporter::finalize()` now checks `gzwrite()`'s return value (a disk-full mid-compression
  used to silently truncate the output with no exception).
- **`DatabaseExporter::quoteValue()` now delegates to `Connection::quote()`** (real `PDO::quote()`,
  driver- and charset-aware) instead of `addslashes()`, which is unsafe for multi-byte charsets whose
  trailing lead-byte range overlaps `0x5C` (GBK, Big5, Shift-JIS).
- **`PreflightService::run()` is now memoized per-instance** - it previously re-ran a full recursive
  filesystem walk plus an `information_schema.tables` query on every call, and a single backup calls
  it from several places (`BackupOrchestrator`'s `startBackup()`/`runCodeArtifact()`/
  `buildManifest()`).

Also found and fixed as part of this work: `DatabaseExporterWebModeKernelTest.php`'s
`testCursorAdvancesAcrossStepsAndSkipsStructureOnlyRows` had a tautological assertion
(`assertSame([], $x === [] ? [] : [])`, which can never fail regardless of `$x`) - replaced with a
real assertion.

**Known latent bug found but NOT fixed here (out of scope for this pass)**: `CodeArchiver`'s
PharData fallback path (`exclusionRegex()`/`archiveViaPharData()`) throws
`RegexIterator::__construct(): Unknown modifier ']'` for at least some real exclusion lists (hit
incidentally while testing the size-ceiling fail-closed behavior, once the flow could actually reach
that far). `archiveViaPharData()`'s existing test coverage only exercises the CLI-available and
over-ceiling-refusal paths, not the PharData-fallback-actually-runs path - see `TODO.md`.

## Post-Slice-3 — HTTPS enforcement, abort-contract, and boundary-validation hardening

Fixes from an external code review of the network/orchestration layer (`DrupalForgeClient`,
`Uploader`, `UploadPlan`, `ArtifactDescriptor`, `BackupManifest`, `PreflightResult`, `BackupBatch`,
`BackupOrchestrator`).

- **HTTPS enforcement**: `DrupalForgeClient` now rejects a non-`https://` base URL with a new
  `InvalidConfigurationException`, checked on every request (including `connect()`) before any
  network call. Closes the one remaining way to violate AGENTS.md's HTTPS-only requirement now that
  the URL field is gone from the admin UI (see the previous entry below) — a bad `settings.php`
  override now fails loudly instead of silently sending the migration secret over cleartext.
- **`BackupBatch`'s web/Batch upload path now shares the abort-on-failure contract**: it used to
  call `Uploader`/`DrupalForgeClient` directly for per-part uploads, bypassing
  `BackupOrchestrator`'s guarded (abort-and-log-on-any-failure) methods entirely — a failed upload
  during the UI-driven flow left a stale DrupalForge reservation and a stale status page instead of
  the documented explicit-abort behavior every other step already had. `BackupOrchestrator` gained
  public `requestUpload()`/`uploadOnePart()`/`uploadArtifact()` guarded wrappers; `BackupBatch` now
  calls through them.
- **`ArtifactDescriptor` round-trips as a keyed array, not an unkeyed tuple**: added
  `toArray()`/`fromArray()`; `BackupBatch`'s three call sites that used to build/destructure a bare
  `[artifact, path, size, sha256]` tuple (a future field reorder would have silently swapped values
  with no type error) now use it.
- **Boundary validation added to the value objects that cross into a DrupalForge request**:
  `ArtifactDescriptor`'s constructor now rejects an unrecognized artifact type, non-positive size,
  or malformed sha256; `BackupManifest`'s constructor now rejects empty docroot/php_version/
  drupal_version or zero artifacts (`fromArray()` used to default every missing field instead of
  throwing); `UploadPlan::fromResponse()` now rejects a degenerate plan (unrecognized mode, an empty
  `parts` array on a multipart plan, or a null `url` on a single-PUT plan) — the exact shape that
  used to let `Uploader` silently report success while transferring zero bytes.
  `BackupOrchestrator::getArtifactPath()` also gained a defensive `match` instead of silently
  mapping any non-`'code'` string to the db path. `PreflightResult`'s loosely-typed `$checks` bag
  was left as-is (documented why in its docblock) — it's internal inter-service data, not data
  crossing the DrupalForge trust boundary.
- **`hash_file(...) ?: ''` fixed in `BackupOrchestrator::resumeUpload()`** and in
  `BackupBatch::dbExportOperation()`'s post-export checksum step (the latter now also explicitly
  aborts the backup, since it runs after `runDbArtifactWebStep()`'s own guard already returned
  successfully): both now check the return value explicitly and throw rather than silently shipping
  an empty checksum.
- **`Uploader`**: an otherwise-2xx PUT response with no `ETag` header (a stripping proxy/CDN) is now
  treated as a failed part, not silently recorded as done with `etag=''`. A `RequestException` with
  no attached response (a low-level transfer failure after the connection was already established,
  e.g. a reset mid-upload) now retries the same as `ConnectException`, instead of being treated as
  an immediate permanent failure the way a real 4xx is.

## Post-Slice-3 — DrupalForge URL is hardcoded, not a form field

- Removed the "DrupalForge URL" field from the settings form and the `url` key from
  `drupalforge_migrate.settings`'s config schema. There is exactly one production DrupalForge, and
  an admin-editable URL field invited accidental misconfiguration (e.g. an `http://` value silently
  sending the migration secret over cleartext).
- `DrupalForgeClient::DEFAULT_URL` hardcodes `https://www.drupalforge.org`. A developer targeting a
  dev/stage DrupalForge instead overrides it in `settings.php`:
  `$settings['drupalforge_migrate_url'] = '...'` — read via `\Drupal\Core\Site\Settings::get()`,
  the standard Drupal convention for a per-environment value that must never be admin-UI-editable
  or exported config.
- Added `DrupalForgeClientInterface::getBaseUrl()` so `MigrationStatusController`'s "View this
  migration on DrupalForge" link sources the same resolved URL as every API call, instead of
  reading the (now-removed) config key directly.

## Slice 3 — Uploader, Batch API, status page (module complete)

- `Uploader` (behind `UploaderInterface`): `uploadArtifact()` (single PUT, or a blocking loop over
  every remaining multipart part - the Drush/CLI path); `uploadOnePart()` (uploads exactly one part
  and persists its ETag via `ProgressStateStore` immediately - the seam `BackupBatch` drives one
  call per Batch API operation); `resumeFrom()` (first part not yet recorded as done). Retries
  (exponential backoff + jitter, via an injectable sleeper so tests never sleep) only on 5xx
  responses or connection-level failures, never on 4xx (e.g. an expired presigned URL is permanent).
  Only one part's worth of bytes (never the whole file) is held in memory at a time; sha256 is
  computed once by the producing service (`CodeArchiver`/`DatabaseExporter`) via `hash_file()`,
  which already streams rather than loading the file into memory.
- `DrupalForgeClientInterface::complete()` implemented: `POST .../backups/{id}/complete` with
  `{artifacts: [{artifact, sha256, parts?}], manifest}`. The `parts` key is included only for
  multipart artifacts; a single-PUT artifact sends just `artifact`/`sha256`. Callers' internal
  `size` key (needed for local manifest-building) is deliberately never sent on the wire.
- `BackupOrchestrator` gained: `runFullBackup()` (produce + upload both artifacts + `completeBackup`
  - the Drush/CLI end-to-end path), `resumeUpload()`/`resumeBackup()` (resume whichever local
  artifacts exist on disk from an interrupted run and finish the backup - deliberately returns the
  upload result array rather than `void`, so the manifest can be built without a second upload),
  `completeFromArtifacts()` (builds the manifest from already-produced Batch-context artifact
  results, for the web path), `completeBackup()` (the only method that can mark a backup `ready`;
  structurally unreachable after any upload failure, since every artifact/upload call is wrapped in
  the same abort-on-throw guard introduced in Slice 2), `hasPendingExportCursor()`.
- `drupalforge-migrate:backup` rewritten to call `runFullBackup()`/`resumeBackup()` directly - it now
  genuinely uploads both artifacts and marks the backup `ready`, closing the Slice 2 limitation.
  `--resume` first finishes any in-progress web-mode DB export cursor, then resumes/finishes
  uploads.
- `BackupBatch`: Batch API bridge for the web path. Upload progress uses the "single operation,
  re-invoked repeatedly via `$context['finished'] < 1`" pattern rather than one static operation
  entry per part (the total part count isn't known until after the artifact is produced and a plan
  is requested). `ProgressStateStore` - not `$context['sandbox']` - is always the source of truth
  for "which parts are done", so a run abandoned and resumed via a fresh Batch (a new page load, a
  new `$context`) never re-uploads a finished part.
- `MigrationStatusController` + `/admin/config/development/drupalforge-migrate/status` (with a
  "Status" local task alongside "Settings"): last backup/step/errors, a "Start backup" action
  (kicks off `BackupBatch::buildOperations()`), a "Resume backup" action shown only when a partial
  upload is detected, and a derived link back to the DrupalForge migration page. `start`/`resume`
  are `_csrf_token`-protected routes (state-changing GET-triggered actions, matching Drupal core's
  own convention for this pattern, e.g. `system.run_cron`).
- **Bug found while wiring the controller:** `ControllerBase` already declares a non-readonly
  `$configFactory` property; a promoted `private readonly ConfigFactoryInterface $configFactory`
  constructor parameter of the same name fatals the class at load time ("Cannot redeclare
  non-readonly property ... as readonly") - this only surfaces once the module is actually
  installed/routes rebuilt, not from PHPUnit alone. Fixed by naming the property
  `$forgeConfigFactory`. Worth flagging as a general gotcha for any Drupal controller using
  constructor property promotion with `readonly`.
- **Bug found while writing `StatusPageTest`:** the status page's "is there something to resume"
  check initially read `last_status['backup_id']`, which only reflects the most recently
  *completed or aborted* backup - an in-progress backup (mid-upload, before any completion/abort)
  has no `last_status` entry yet, so the "Resume backup" action never appeared. Fixed by preferring
  `ProgressStateStore::getCurrentBackupId()` and falling back to `last_status` only once there is no
  current backup.
- Full manual E2E smoke test against the real DDEV site and a real (not mocked) throwaway fake
  DrupalForge API + local HTTP storage endpoint: a genuine ~33MB multipart code-archive upload (64
  real HTTP PUTs) was reassembled byte-for-byte from the storage endpoint and its sha256 matched
  what `complete()` recorded; a backup was killed mid-upload with `pkill -9` from inside the
  container (a real process kill, not a simulated one) and `--resume` correctly continued from the
  next un-recorded part rather than re-uploading finished ones (only the single in-flight part at
  the moment of the kill was re-sent - the exact "at most one part's progress" bound the design
  targets); a forced real HTTP 403 on a part correctly failed with no retry, called `abort()`
  (`DELETE`, confirmed via the fake API's own state - the reservation was removed entirely rather
  than left dangling), and never called `complete()`.

## Slice 2 — Archiver, exporter, and Drush backup

- `BackupManifest` value object (manifest.json (de)serialization, round-trip tested).
- `CodeArchiver` (behind `CodeArchiverInterface`): exclusion rules (`sites/*/files` per site
  directory, private files path, `.git`, `node_modules`, `vendor` only when no `composer.lock`,
  `settings.php`/`settings.*.php` tracked separately as excluded settings files); CLI `tar | gzip`
  path when both binaries are available, PHP `PharData` fallback under a configurable size
  ceiling otherwise; `manifest.json` written as a sibling file next to the archive (not embedded
  in the tar, to avoid re-opening an already-closed archive).
- `DatabaseExporter` (behind `DatabaseExporterInterface`): CLI mode (`mysqldump | gzip`, credentials
  passed via a temporary `--defaults-extra-file` rather than a `-p` CLI arg, so the password never
  appears in `ps`); web/batch mode (`exportStepWeb()`) that dumps one table (or table-structure)
  per bounded call, writing plain SQL to an uncompressed sibling file across calls and gzip-
  compressing only once finished, with cursor state persisted via `ProgressStateStore` so it
  survives across separate requests; structure-only handling for `cache_*`/`watchdog`/`sessions`/
  `queue`/`semaphore`/`flood`/`cachetags` tables.
- `ProgressStateStore`: namespaced `State` wrapper for the current backup id, the DB export
  cursor, per-artifact upload state (stubbed for Slice 3), and the last recorded status.
- `BackupOrchestrator`: the shared entry point (`preflight`, `startBackup`, `runCodeArtifact`,
  `runDbArtifactCli`/`runDbArtifactWebStep`, `abortBackup`, `status`) that both the Drush command
  and the future Batch API path call, wrapping every artifact step so a failure always aborts the
  reservation with a specific, named reason recorded via `ProgressStateStore`.
- `drupalforge-migrate:backup` (`--db-only`, `--code-only`, `--resume`), `:status`, `:list` Drush
  commands. **Known limitation:** `:backup` produces artifacts locally only - it does not upload
  them or call DrupalForge's `complete` endpoint (Uploader ships in Slice 3), so it never marks a
  backup `ready`.
- `CodeArchiverInterface` / `DatabaseExporterInterface` added (mirroring the `ShellRunnerInterface`
  / `DrupalForgeClientInterface` pattern from Slice 1) so `BackupOrchestrator`'s failure-handling
  behavior (abort-on-failure with a named reason) can be tested against fakes without PHPUnit
  needing to double the `final` `CodeArchiver`/`DatabaseExporter` classes.
- **Bug found and fixed while smoke-testing against a real ~150MB codebase:** `ShellRunner`'s
  `runPiped()` wrote a command's entire stdout into the next command's stdin before reading any of
  its output - for any payload larger than the OS pipe buffer (~64KB), the writer and the
  downstream reader (e.g. `gzip`) deadlock permanently once both fill their respective pipe
  buffers. Fixed with a `stream_select()`-based read/write loop
  (`ShellRunnerLargePipeTest` reproduces it with 8MB of `/dev/urandom` piped through `gzip` -
  incompressible data is required to reproduce it, since gzip's output must also be large enough
  to fill its own stdout pipe).
- **Bug found and fixed:** `DrupalForgeClient` only caught `GuzzleHttp\Exception\RequestException`,
  but `ConnectException` (thrown when DrupalForge is unreachable - DNS failure, connection
  refused, timeout) extends `TransferException`, not `RequestException`, so it escaped uncaught
  instead of surfacing as a `DrupalForgeApiException`. This is the single most common real-world
  failure mode (an unconfigured or down DrupalForge endpoint); fixed by catching the shared
  `GuzzleException` interface instead (`DrupalForgeClientTest::testConnectionFailureIsWrappedAsApiExceptionNotUncaught`).
- Manual smoke test against the real DDEV site (Drupal 10.6.18, MariaDB): `preflight`, `backup
  --code-only` (33MB real tar.gz), `backup --db-only` (real `mysqldump` output verified),
  `backup --resume --db-only` (web-mode cursor resume), `status`, `list` all exercised against a
  throwaway local fake DrupalForge API.

## Slice 1 — Skeleton, preflight, and DrupalForge connection

- Module skeleton (`info.yml`, `services.yml`, `routing.yml`, `permissions.yml`, `links.menu.yml`,
  `.module`, `composer.json` with zero runtime dependencies beyond `php: >=8.1`, config schema
  restricted to `url`/`migration_id`).
- `ShellRunner`: safe shell-out primitive (`escapeshellarg`, `proc_open`, try/catch, piped chains).
- `PreflightResult` value object and `PreflightService`: docroot/project-root detection, PHP/DB
  driver/CLI-tool checks, size estimation; reports unsupported with a named reason rather than
  guessing.
- `ArtifactDescriptor` / `UploadPlan` value objects.
- `DrupalForgeClient` (behind a `DrupalForgeClientInterface`, so it can be swapped for a fake in
  tests): `connect`/`listBackups`/`reserveBackup`/`requestUpload`/`abort` against the DrupalForge
  migration API contract, with the secret read exclusively from `State`.
- `DrupalForgeMigrateSettingsForm`: URL/Migration ID/Secret fields plus "Test connection".
- `drupalforge-migrate:preflight` Drush command, under `src/Drush/Commands/` (Drush 13's actual
  auto-discovery convention - a plain `services.yml` entry tagged `drush.command` is *not*
  discovered; only `<module>.drush.services.yml` or the `src/Drush/Commands/*Commands.php`
  path convention are).
- `drupalforge_migrate_test_support` companion module for faking `DrupalForgeClient` responses in
  functional tests, via Symfony service decoration (requires `ShellRunnerInterface` /
  `DrupalForgeClientInterface`, since PHPUnit/Symfony cannot mock or decorate `final` classes).
- Site-level `require-dev` additions needed to run this module's tests in place:
  `phpunit/phpunit:^9.6`, `phpspec/prophecy-phpunit:^2.4`, `drupal/core-dev:^10.6` (the latter
  pulls in Mink/BrowserKit for `BrowserTestBase`).
